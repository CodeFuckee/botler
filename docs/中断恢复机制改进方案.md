## 1. 问题背景

Botler 以「断点续跑」（issue #8 / #47 / #84）作为任务中断恢复机制：平台进程
重启（CI/CD 频繁重新部署）时，调度器把 `running / retrying` 任务标记
`interrupted` 并重新入队（`scheduler.start → database.requeue_interrupted`），
恢复执行时按引擎接续上次会话：

| 引擎 | 落库字段 | 恢复方式 |
|---|---|---|
| claude（issue #8） | `tasks.claude_session_id` | `claude -p --resume <sid>` 接续上次会话，工作区保留 |
| hermes（issue #47） | `tasks.hermes_history`（`{session_id, messages}` JSON） | `AIAgent(session_id=..., conversation_history=历史)` |
| dsh（issue #84） | `tasks.dsh_session_id` | SDK 以同一 session id 在 `session_root` 接续会话（v1.1：id 任务开始即落库、SDK resume，见 §4.7） |

恢复时统一追加 `_resume_prompt`（`config.templates.resume` 可编辑，默认
`DEFAULT_RESUME_PROMPT`）引导 agent：

> 上次处理因平台重新部署而中断，你的对话与工作区改动已保留。请先检查当前状态
> （git status / git log / 未提交改动），弄清上次做到哪一步，然后从断点继续：
> 完成剩余的修复/实现 → 自测 → 推送 → 在 issue 上留结果评论。
> 不要从零重新分析 issue（除非确认上次未开始实质工作），不要重复已经完成的工作。

### 1.1 现象

线上频繁出现：中断恢复后 agent **反复检查实现状态、反复重新实现**，表现为
重复读 diff、重复跑测试、重复写相同代码，浪费 token 与时间，甚至出现
「把上次已完成的实现推翻重写」。

### 1.2 根因分析（对照代码）

1. **恢复状态只有「对话转录」，没有「任务进度」**：平台只持久化会话 id /
   消息历史（`claude_session_id` / `hermes_history` / `dsh_session_id`），
   「计划、已完成步骤、验证证据、产物清单」全部隐含在对话里，不落库。
2. **恢复 = 提示词驱动模型「自查反推」**：`DEFAULT_RESUME_PROMPT` 让模型
   自己 `git status / git log / 看未提交改动` 反推进度。LLM 反推不可靠
   （无法区分「我上次的未提交改动」与「已提交/上游改动」，也无法确认测试
   是否跑过），必然反复检查；反推不确定时模型倾向「多验一遍 / 多做一遍」。
3. **验证状态不持久化**：测试是否执行过、结果如何、哪个命令验证过没有记录；
   恢复后只能全部重跑。
4. **降级路径语义矛盾**：claude 会话文件丢失时清除 `claude_session_id`
   降级为全新会话（hermes 无消息时同理），但恢复引导语仍声称「对话与工作区
   改动已保留……不要重复已经完成的工作」——模型实际没有任何历史，既无法
   知道完成了什么，又被告知不要重做，只能从零重分析（= 重复实现）。
5. **会话发现靠手工传递 id**：三套字段（`claude_session_id` /
   `dsh_session_id` / `hermes_history`）由各引擎在「上次执行正常结束/超时/
   强杀路径」上解析落库；任何一环解析失败即断链，无自动发现能力。
6. **工作区无快照**：续跑依赖「未提交改动在重部署后幸存」；若重部署重建
   工作区（克隆丢失），改动全失 → 全量重来。

7. **dsh 会话 id「执行结束后」才落库（强杀必丢）**：`dsh_session_id` 由
   `_persist_dsh_session_id` 在 run 收尾（正常/停止/超时）时从结果行解析写入；
   平台重启、进程被强杀时收尾代码根本不会执行 → 会话 id 未落库，恢复退化为
   「全新会话 + 自查反推」，是 dsh 引擎「重复实现」的直接来源。对照 CLI 侧
   `dsh --profile tui --resume <id>` 的恢复语义是「先有 id 再续跑」，Botler
   缺「先落 id 再开跑」的闭环（v1.1 补充，见 §4.7）。

## 2. hermes -c 机制拆解（借鉴对象）

`hermes -c`（等价 `hermes --resume latest`，`hermes -c "name"` 按名续跑）
的核心不是「命令本身」，而是其背后的**会话状态基础设施**：

| hermes 能力 | 行为 | 对 Botler 的启发 |
|---|---|---|
| `-c` / `--resume latest` | 自动解析「最近一次会话」，调用方无需保存并传入 session id | 会话发现应自动化，而不是手工落库传参 |
| `--in DIR` | 把「最近会话」的查找范围限定到指定工作区 | 按 `(repo, workdir, issue)` 维度定位会话 |
| SessionDB 血缘链（`parent_session_id`） | 会话被自动压缩/轮转后 fork 子会话，`resolve_resume_session_id` 沿血缘链定位「持有最新消息的后代会话」 | 恢复目标必须解析到「仍存活的有效会话」，而不是死 id |
| 恢复完整上下文 | 恢复对话历史 + 记录的工作目录（`--no-restore-cwd` 可跳过） | 恢复语义是「状态还原」，不依赖模型自查 |
| checkpoints 子系统 | 破坏性文件操作前落文件系统检查点，`/rollback` 可回滚，`hermes checkpoints prune` 清理 | 工作区状态要可快照、可回滚、可回收 |

一句话：**hermes 的恢复是「状态索引自动解析 + 完整上下文还原」，Botler 目前
是「id 手工传递 + 提示词让模型反推」**——前者确定性，后者概率性，概率性正是
「反复检查实现和重复实现」的来源。

## 3. 设计目标

1. **恢复即状态恢复**：恢复后 agent 直接拿到「已完成步骤 + 验证证据 / 下一步
   动作」的确定性交接单，禁止重做已完成步骤；
2. **验证证据可复用**：已执行且通过的测试/构建不再重跑；
3. **会话发现自动化**（hermes -c 式）：按工作区/血缘自动解析最近有效会话，
   消除手工 id 传递与断链；
4. **工作区可快照回滚**：不再依赖「未提交改动在重部署后幸存」；
5. **三引擎统一语义**：claude / hermes / dsh 共用同一套「进度账本 +
   会话注册表 + 检查点」抽象，仅在底层恢复参数上分引擎适配；
6. **降级路径明确且诚实**：任一状态缺失时走明确降级阶梯，恢复引导语如实
   说明「有什么/没什么」，杜绝「假装有历史」的矛盾指令。

## 4. 推荐方案：结构化进度账本 + 会话自动发现 + 工作区检查点 + 确定性恢复握手

### 4.1 结构化任务进度账本（task_progress）

新增 SQLite 表，记录任务级「进度 + 验证证据」，与对话转录解耦：

```sql
CREATE TABLE task_progress (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id     INTEGER NOT NULL REFERENCES tasks(id),
  step_no     INTEGER NOT NULL,               -- 步骤序号
  step_desc   TEXT    NOT NULL,               -- 步骤描述（做了什么/要做什么）
  status      TEXT    NOT NULL,               -- pending / done / failed / skipped
  evidence    TEXT,                           -- JSON：验证命令/退出码/输出摘要/哈希
  files       TEXT,                           -- JSON：本步骤涉及文件清单
  verified_at TEXT,                           -- 验证通过时间
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);
CREATE INDEX idx_task_progress_task ON task_progress(task_id, step_no);
```

要点：

- **写入时机**：任务开始（写入初始步骤计划）、每个步骤完成/失败（引擎回调）、
  任务收尾；停止/超时路径同样在终止前补写「进行到哪一步」（对齐 issue #35
  停止语义）。落库用 issue #181 的「原子写」模式，中断不污染账本。
- **进度来源（三选一，按引擎能力适配）**：
  - 平台侧约定：任务提示词模版新增「进度上报」节，要求 agent 每个里程碑
    用固定格式（如 `[PROGRESS] step=2 status=done evidence="pytest -q 通过"`）
    输出，executor 解析并落库（对 claude / hermes / dsh 通用，改动最小）；
  - 工具化上报：给 agent 暴露一个 `report_progress` 工具（hermes/dsh 原生
    支持工具调用，claude 用 `claude -p --tools`），结构化更强；
  - SDK 回调：hermes/dsh 引擎从 `run_conversation` 返回的 messages 中
    增量解析 `[PROGRESS]` 标记（复用 `_hermes_history_from_output` 通道）。
- **只增不改**：历史步骤追加新状态行（快照式），保留「上次怎么做的」可追溯，
  恢复时取每步最新状态。

### 4.2 会话自动发现（session registry，hermes -c 式）

新增 `task_sessions` 注册表，替代三套手工 id 字段的「唯一事实源」：

```sql
CREATE TABLE task_sessions (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id      INTEGER NOT NULL REFERENCES tasks(id),
  engine       TEXT    NOT NULL,              -- claude / hermes / dsh
  workdir      TEXT    NOT NULL,              -- 任务工作区（定位维度）
  issue_iid    INTEGER NOT NULL,              -- 定位维度
  session_id   TEXT,                          -- 引擎会话 id（claude/dsh）
  history      TEXT,                          -- hermes 消息历史 JSON（可选）
  parent_id    TEXT,                          -- 血缘：会话被压缩/轮转时的父 id
  valid        INTEGER NOT NULL DEFAULT 1,    -- 有效性（会话文件存在/可加载）
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL
);
CREATE INDEX idx_task_sessions_loc ON task_sessions(workdir, issue_iid, updated_at);
```

恢复解析规则（对齐 `hermes --resume latest --in DIR`）：

1. 按 `(workdir, issue_iid)` 取 `updated_at` 最新、`valid=1` 的会话；
2. claude：校验 `~/.claude/projects/*/<sid>.jsonl` 存在（沿用 `_session_file`），
   不存在则标记 `valid=0` 并继续向前找更早会话；
3. 血缘链：参考 hermes `resolve_resume_session_id`，若最新会话是「被压缩后
   fork 出的空壳父会话」，沿 `parent_id` 链解析到持有最新消息的后代会话；
4. 全部失效 → 明确记录降级原因，走 §4.6 降级阶梯。

三引擎适配：claude 用 `--resume <sid>`；hermes 用 `session_id + history`
（沿用 `_hermes_resume_data`）；dsh 用 SDK session id——v1.1 起**任务开始即
落库、恢复经 SDK resume**（见 §4.7，等价 CLI `dsh --profile tui --resume <id>`
语义）。新增引擎插件（issue #140 插件体系）自动获得同一套注册表能力。

### 4.3 工作区检查点（workspace checkpoint）

- **落点**：任务开始前、每次进度上报后、每次提交前，对工作区打快照
  （`git bundle` 全量 + 未提交改动 tar 包，或直接 `git stash` + 快照提交），
  存放 `cache/checkpoints/<task_id>/`（与 `cache/` 同级目录，配置可改）；
- **恢复**：`prepare_workspace(resume=True)` 前先检查工作区完整性，若被清空/
  损坏 → 从最近检查点还原，替代「依赖未提交改动幸存」；
- **回收**：任务终态（succeeded/failed）后按保留天数/总大小上限清理，
  对齐 `hermes checkpoints prune` 策略；
- **回滚**：为后续「agent 破坏性操作回滚」预留（本期仅快照/还原）。

### 4.4 确定性恢复握手（resume handoff）

用「状态交接单」渲染替代（或增强）现有 `DEFAULT_RESUME_PROMPT`，数据源 =
§4.1 账本 + §4.2 注册表 + §4.3 检查点元信息：

```text
【继续处理（中断恢复）】issue #{issue_iid}「{issue_title}」
平台已恢复以下确定性状态（非模型自查结果）：
- 上次执行到：步骤 2「修复 xxx」→ 状态 done，证据：pytest -q 通过（2026-08-18 09:00）
- 未完成：步骤 3「补充边界测试」→ 下一步
- 已验命令：pytest -q（工作区文件哈希与验证时一致，无需重跑）
- 工作区：已由平台从检查点恢复/保留，git status 如下……
要求：只执行下一步（步骤 3），禁止重新检查/重做步骤 1-2。
```

- 账本为空（确属首次/状态丢失）→ 如实降级为「全新会话」引导语，不再声称
  「对话与工作区改动已保留」；
- 模板保留用户可编辑能力（`config.templates.resume` 升级为交接单渲染，占位符
  机制不变，issue #116 兼容）。

### 4.5 验证证据复用

- 每步验证动作记录 `evidence`（命令 / 退出码 / 输出摘要 / 相关文件哈希）；
- 恢复时若「待验证文件哈希」与账本记录一致 → 该步骤验证结果视为有效，交接单
  标注「已验，勿重跑」；
- 哈希不一致（上游被拉新、文件被改动）→ 标注「需重新验证」，诚实指引。

### 4.6 统一降级阶梯

| 可用状态 | 恢复方式 | 引导语 |
|---|---|---|
| 账本 + 会话 + 检查点 | 完整恢复：还原工作区 + 接续会话 + 交接单 | 「已完成/下一步」确定性指引 |
| 账本 + 工作区（会话丢失） | 全新会话 + 交接单 | 明确「对话已丢失，但进度如下，直接做下一步」 |
| 仅检查点 | 还原工作区 + 全新会话 | 明确「工作区已还原至检查点，进度未知，重新梳理」 |
| 全部丢失 | 全新会话 + 全新工作区 | 首次任务引导语（如实说明） |

每级降级都写日志与 `task_logs`，供问题排查（对齐 issue #280 的可观测性要求）。

### 4.7 dsh 引擎先行：会话 id 任务开始即落库 + SDK resume（issue #281 用户补充意见）

用户补充意见（issue #281 评论）：**DeepSeek Harness SDK 引擎先行**；DeepSeek
同样具备 `dsh --profile tui --resume <id>` 的 resume 命令；希望**每次任务开始
时把会话 id 写入任务详情**，终端恢复后若发现会话 id，**直接用该 id resume 继续
任务，并以 DeepSeek Harness SDK 方式实现，而非 CLI 方式**。据此把 §4 的通用
方案在 **dsh 引擎上先行落地**，具体增量：

1. **会话 id 前置落库（先落 id 再开跑）**：
   - 任务开始（`_run_dsh_once` 构造 `DshRunner` 之前）即获取会话 id：恢复
     场景直接复用 `tasks.dsh_session_id` 已落库 id；新建任务先预生成 id
     （形如 `botler-<task_id>-<ts>-<rand>`）或经 SDK 会话创建接口获取
     （Phase 1 开工前做 SDK 能力探测，见 §8 问题 5）；
   - 立即原子写 `tasks.dsh_session_id`（复用 issue #181 原子写模式），并在
     任务详情接口/页面展示「dsh 会话 id」字段（task 详情已返回该列，前端
     补展示即可）——**任何时刻被强杀/重启，会话 id 都已落库可恢复**；
   - 写入失败 = 任务失败（不静默降级，避免「以为能恢复、实际不能」）。
2. **以 id 启动 SDK 会话**：`DshRunner(session_id=<id>)` 调
   `harness.run(prompt, session_id=<id>)`——新建任务以预生成 id 创建会话，
   恢复任务以已落库 id 接续会话，SDK 同一参数承载两种语义，无需起 CLI
   子进程。
3. **恢复路径（终端/进程重启后）**：
   - 调度器 `requeue_interrupted` 重新入队 → `_run_dsh_once` 读到
     `tasks.dsh_session_id` 非空 → 校验 `session_root` 下会话文件存在
     （可加载）→ `DshRunner(session_id=<id>)` **SDK 进程内 resume**，追加
     `_resume_prompt`（后续升级为 §4.4 交接单）；
   - 语义对照：CLI `dsh --profile tui --resume <id>` 的「用 id 续跑」在 SDK
     侧即 `run(session_id=<id>)`；差异仅在承载方式（CLI 独立子进程 vs SDK
     进程内）。Botler 采用 SDK 方式（issue #84 已内建，停止/超时强杀语义、
     事件行协议、日志落盘全部复用，无需新协议）；
   - 会话文件缺失/不可加载 → 标记 `valid=0` 并如实降级（§4.6），引导语
     不得再声称「对话与改动已保留」。
4. **Phase 1 范围（dsh 先行）**：§4.1 进度账本 + §4.4 交接单 + 本节的「id
   前置落库 + SDK resume」在 dsh 引擎完整落地；claude / hermes 保持现状，
   待 Phase 2 会话注册表统一后并入同一抽象（各自恢复参数不变）。

## 5. 备选方案对比

| 方案 | 思路 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **A：现状微调** | 只优化 `DEFAULT_RESUME_PROMPT`（如强调「先 git diff 确认已完成」） | 低 | 低：治标，模型仍靠反推，反复检查无法根除 | 无 |
| **B：状态机恢复（推荐，§4）** | 进度账本 + 会话注册表 + 工作区检查点 + 确定性交接单 | 中 | 高：恢复确定性，直接消除「反复检查/重复实现」 | 需要改造 executor 与三引擎插件，需回归 |
| **C：agent 内建 checkpoint 工具** | 给 agent 暴露 save/rollback 检查点工具，让 agent 自己管理状态（hermes checkpoints 风格） | 高 | 高：最灵活，agent 可精确回滚 | 依赖 agent 自律，不可靠路径多，与平台调度耦合深 |

推荐 **方案 B**，并在 Phase 3 预留方案 C 的接口（检查点工具）。

## 9. 结论

当前「断点续跑」把恢复语义压在「模型从 git 工作区反推进度」上，是
「反复检查实现和重复实现」的根因。借鉴 `hermes -c` 的「会话自动发现 +
完整状态还原」思路，把恢复从「提示词自查」升级为「确定性状态交接」：
结构化进度账本记录做了什么、会话注册表自动定位最近有效会话、工作区检查点
保证可还原、恢复交接单给出唯一下一步。结合 issue #281 用户补充意见，落地
优先序调整为 **dsh（DeepSeek Harness SDK）先行**：任务开始即把会话 id 写入
任务详情，终端恢复后凭已落库 id 经 SDK resume 续跑（等价 `dsh --profile tui
--resume <id>`，以 SDK 方式而非 CLI 方式实现），先消除「中断即丢 id → 全新
会话 → 重复实现」这一最直接的来源，再按 Phase 2→3 补齐会话注册表与工作区
检查点。按 Phase 1→2→3 落地即可系统性消除该问题；本期仅出方案，不实现。
