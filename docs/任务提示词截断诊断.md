# 任务 #82 提示词截断问题诊断报告

> 日期: 2026-08-14 | 状态: 诊断完成（修复未实施，修复方案存档于第 5 节）
> 结论: **提示词数据没有被截断，是任务详情页显示不全**

## 1. 问题现象

用户报告：#82 号任务发送的提示词被截断，与全局模版不一致。

编号说明（避免混淆）：

| 编号 | 含义 |
|---|---|
| #82 | botler `tasks` 表主键 id（数据库自增主键，第 82 行） |
| #55 | 该任务对应的 GitLab issue iid（"全局模版取消内层的垂直滚动"） |

即：任务 #82（`tasks.id=82`）处理的是 GitLab issue #55，两者不是同一个 82。

## 2. 诊断结论（TL;DR）

**发送给 AI 的提示词完整无截断**：实际发送内容 7066 字符，与全局模版**逐字节相等**。用户看到的"截断"发生在任务详情页的**展示层**，根因两处：

1. 聊天记录 API 对每条消息硬截断到 5000 字符（提示词 7066 > 5000），且前端不渲染"已截断"标记，用户无感知；
2. "查看提示词"按钮是摆设——后端从不返回 `prompt` 字段，点开永远显示"（提示词未持久化，见执行日志）"占位文案。

## 3. 证据链

三处数据对比：

| 数据源 | 字符数 | 结果 |
|---|---|---|
| 全局模版 `data/backend/config.yaml` → `templates.default` | 7066 | — |
| 实际发送的提示词（会话文件首条 user 消息） | 7066 | **逐字节相等** ✓ |
| 详情页聊天记录展示的提示词（API 返回） | 5000 | 被 `_TRANSCRIPT_MAX_TEXT` 截断 ❌ |

验证命令：

```bash
# 查任务记录（id=82 ↔ issue_iid=55）
sqlite3 /home/ckd/codes/botler/data/backend/botler.db \
  "SELECT id, issue_iid, issue_title, status, claude_session_id FROM tasks WHERE id=82;"

# 全局模版（7066 字符）
# 实际发送的提示词：会话文件首条 user 消息，全文完整
# ~/.claude/projects/-home-ckd-codes-botler/777128fe-a4e6-415e-af2e-af9871007c39.jsonl

# 详情页展示的（被截断）聊天记录
curl -s http://localhost:<port>/api/tasks/82/execution | jq '.transcript[0] | {len: (.text|length), truncated}'
# → len: 5000, truncated: true
```

Python 对比脚本已验证 `会话首条 user 消息 == 全局模版`（逐字节相等）。

背景补充：提示词全文**不落库**——`tasks` 表（`backend/botler/database.py:58-76`）无 prompt 列，渲染后的完整提示词仅存在于 Claude 会话 jsonl 文件中（任务创建时由 `executor._build_prompt` 构造后经 argv 传给 `claude -p`）。全局模版在 8/12 之后被改长过（备份 `config.yaml.bak-1144` 中模版为 5005 字符），现为 7066 字符，超过了展示层 5000 字符上限，从而触发该现象。

## 4. 根因分析

### 4.1 聊天记录 5000 字符硬截断 + 前端无截断标记（直接原因）

- `backend/botler/executor.py:206`：`_TRANSCRIPT_MAX_TEXT = 5000` —— 每条消息文本的展示截断上限
- `executor.py:240-244` `_truncate_text()`：`text[:max_chars]` 硬切片
- `executor.py:303`（user 消息，content 为 list）、`executor.py:316`（user 消息，content 为 str）等：所有消息统一套用该截断，返回 `truncated: True`
- 前端 `frontend/src/pages/TaskDetail.jsx:8-33` `LiveMsg` 组件：**从不渲染 `truncated` 字段**，`pollLive`（`TaskDetail.jsx:143`）也丢弃 API 的 `transcript_truncated` —— 用户看到被腰斩的提示词却没有任何提示

截断点位置：提示词从 §3.2 中部（"推送后必须用 `GITLAB_HOST=…glab ci status --branch`"那句附近）被切掉，§3.2 后半到 §6 约 2066 字符全部丢失，与用户"与全局模版不一致"的观感吻合。

另注：`_TRANSCRIPT_MAX_MESSAGES = 500`（executor.py:205）只保留会话最后 500 条消息，长任务下早期消息可能整体丢失，同样只影响展示。

### 4.2 "查看提示词"按钮永远显示占位文案

- 前端 `TaskDetail.jsx:236-243`：点击后渲染 `task.prompt || '（提示词未持久化，见执行日志）'`
- 后端 `backend/botler/api/tasks.py:49-84` `_task_to_dict()`：**不返回 prompt 字段**（`tasks` 表也没有该列）
- 结果：`task.prompt` 恒为 `undefined`，按钮点开永远只有占位文案，用户无法在页面上看到完整提示词与全局模版比对

### 4.3 排除项（与本次现象无关）

- **发送路径无截断**：`_build_prompt`（executor.py:530-534）→ argv/stdin 全程无长度限制；7066 字符远低于 Linux 单参数上限（MAX_ARG_STRLEN ≈128KB）
- **会话里的 295 字符短提示词**：`RESUME_PROMPT`（executor.py:64）断点续跑的中断恢复提示，设计如此，非截断
- **CSS 无截断**：提示词 `<pre>` 用 `.log-view-flat`（无 max-height），`.pre-wrap` 仅 `white-space: pre-wrap`，无 ellipsis
- **模版页默认折叠**（issue #55/#56 相关 commit）已恢复默认展开，与任务详情页无关

## 5. 修复方案（存档，未实施）

### 方案一：修复展示层（推荐，改动小，历史任务立即受益）

1. **首条 user 消息（提示词）不截断**：`parse_transcript` 对首条 user 消息跳过 `_truncate_text`（或单独提高上限），保持聊天记录中提示词完整；
2. **"查看提示词"按钮真实展示**：后端从会话文件读取首条 user 消息全文（如 `GET /api/tasks/{id}/execution` 响应增加 `prompt` 字段，或独立端点），前端点击按钮时懒加载完整提示词；
3. **截断标记（已选定）**：前端 `LiveMsg` / `EventRow` 渲染 `truncated` 标记（如"（内容过长，已截断）"），其余被截断的长消息（工具结果、长回复）不再被误认为数据丢失。

涉及文件：`backend/botler/executor.py`、`backend/botler/api/tasks.py`、`frontend/src/pages/TaskDetail.jsx`。

### 方案二：提示词持久化到数据库（治本但重）

任务创建时把渲染后的完整提示词存入 `tasks` 表新字段（`prompt`），前端 `task.prompt` 直接读取。需要 schema 变更 + 迁移；仅对新任务生效，历史任务仍需方案一的读会话文件方式兜底。可作为方案一的后续增强。

## 6. 修复后验证方法

1. 打开任务 #82 详情页，点"查看提示词"：内容应与全局模版（`data/backend/config.yaml` → `templates.default`）逐字节一致，长度 7066；
2. 聊天记录首条 user 消息完整显示到 §6 结尾，不再停在 §3.2 中部；
3. 任一被截断的长消息（如大段工具结果）旁出现"已截断"标记；
4. 运行后端测试（`cd backend && pytest`）确保 `parse_transcript` 行为改动不破坏现有用例。
