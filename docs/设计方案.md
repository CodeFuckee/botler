# Botler — GitLab AI Issue Bot 平台设计方案

> 版本: v1.0 | 日期: 2026-08-10 | 状态: 已通过 grill 会话确认需求
> 项目名: **Botler**（Bot + Butler，机器人管家）

## 1. 项目概述

一个运行在服务器上的自动化平台：

- 统一配置多个 GitLab 代码仓库（自建 GitLab CE）
- 统一管理 GitLab 身份认证（单个 bot 账号，一个 token 打天下）
- 通过 webhook 实时监控各仓库的 issue
- 当 issue 被指派给 bot 账号时，自动调用 **Claude Code CLI（无头模式）** 处理该 issue
- Claude Code 按提示词模版规定：解决后直接推送 main 分支，并调用 GitLab API 关闭 issue
- 提供 Web 管理界面 + 配置文件双支持

```
│                                             │
│  FastAPI + SQLite + React Web UI            │
└─────────────────────────────────────────────┘

   │ ④ Claude Code 调 API 关闭 issue
   ▼
GitLab 仓库
```

**端到端时序：**

1. 用户在 GitLab 把 issue 指派给 bot 账号
2. GitLab 推送 webhook 事件（`issue` 事件，`assignee_ids` 变化）到平台
3. 平台校验 webhook secret → 查询任务表去重（防止重复入队）→ 加入该仓库的串行队列
4. 调度器取出任务 → 渲染提示词（全局/仓库模版 + 变量）→ 准备干净工作区 → 执行 `claude -p`
5. Claude Code 按模版规定：分析 → 改代码 → 自测 → 推 main → 调 GitLab API 关闭 issue
6. 执行器收集结果：
   - 成功（exit 0）→ 任务标记 succeeded，记录日志
   - 失败 → 清理工作区，重试（最多 2 次）→ 仍失败：在 issue 上留失败评论 + 打失败标签

## 4. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | Python FastAPI | 与用户其他项目一致，生态成熟 |
| 前端 | React (Vite) | 与用户其他项目一致 |
| 鸿蒙端 | HarmonyOS NEXT（Web 套壳，issue #173） | 系统 Web 组件加载 Web 前端，零成本复用全部 Web 能力；CI 用 hvigorw 真实编译门禁 |
| 数据库 | SQLite | 单机部署、无并发写压力，零运维 |
| 任务执行 | Claude Code CLI 无头模式 | 久经考验、功能全、JSON 结构化输出 |
| 配置 | config.yaml 为唯一事实来源 | 界面写入配置、可版本管理 |
| 部署 | pm2 或 systemd | 用户熟悉 pm2 工作流 |

## 5. 核心模块设计

### 5.1 配置管理

`config.yaml` 为唯一事实来源，Web UI 是编辑它的外壳。

```yaml
# 全局配置
gitlab:
  url: https://home.chenkaidi.top:509
  bot_token: ${GITLAB_BOT_TOKEN}   # 引用环境变量，不落明文
  webhook_secret: ${WEBHOOK_SECRET}

worker:
  max_concurrent_repos: 3     # 跨仓库并行上限
  task_timeout_seconds: 1800  # 单任务超时 30 分钟
  max_retries: 2              # 失败重试次数
  reconcile_interval_seconds: 300  # 对账兜底扫描间隔

claude:
  command: claude
  args: ["-p", "--output-format", "stream-json", "--verbose"]
  # stream-json 逐行实时输出（实时输出功能）：任务页面逐事件查看执行
  # 过程；claude 2.1.x 要求 stream-json 配 --verbose
  # Claude Code 的 DeepSeek 认证继承自服务器环境变量
  # (ANTHROPIC_BASE_URL / ANTHROPIC_API_KEY / ANTHROPIC_MODEL)

templates:
  default: |                    # 全局默认提示词模版
    ...

repos:
  - project_id: 1               # GitLab 项目 ID
    name: shipyard-backend
    url: https://home.chenkaidi.top:509/group/shipyard.git
    enabled: true
    prompt_template: |          # 可选：仓库级覆盖
      ...
```

### 5.2 GitLab 集成层

- 封装 GitLab REST API（`/api/v4`）
- 统一身份：bot 账号 PAT，scope 至少 `api` + `write_repository`
- bot 账号在各仓库的角色：**Maintainer**（原因：webhook 的创建/管理需要 Maintainer/Owner 权限；同时 Maintainer 对未保护 main 有推送权、可管理 issue）
- 提供能力：
  - 添加仓库时自动注册 webhook（`push` 之外的 `issues` 事件）
  - 获取 issue 详情、修改 issue 状态（重试时查状态用）
  - 列出项目、验证 token 连通性

### 5.3 事件入口

**Webhook 接收器** (`POST /webhook/gitlab`)：
- 校验 `X-Gitlab-Token` 请求头与配置的 secret 一致
- 过滤事件：仅处理 `issues` 事件且 action 为 `assignee` 相关（`assignee changed` / `opened`）
- 判定：事件的 `assignee_ids` 或 issue 当前 assignee 是否包含 bot 账号 ID
- 去重：以 `(project_id, issue_iid)` 查任务表，已有 queued/running 任务则跳过

**对账兜底调度器**（APScheduler 每 5 分钟）：
- 遍历启用中的仓库，调 API 查所有 open issues
- 找出「assignee 是 bot 但任务表里没有 queued/running 记录」的 issue 补入队
- **跳过带 `bot-done` / `bot-failed` 标签的 issue**（issue #30）：已完成待用户确认、
  失败待人工介入的工作不再重复领取（webhook 入队同样过滤，且以 API 最新标签为准）
- 解决 webhook 丢事件 / 平台重启窗口期漏任务的问题

### 5.4 任务调度器

- 每个仓库一个队列；调度器保证同一仓库同一时刻最多一个 running 任务
- 不同仓库的任务可并行（受 `max_concurrent_repos` 限制）
- 派发顺序：仓库优先级（1~999 数字小先，issue #51）→ 仓库队列内按
  任务人工优先级（issue #242）→ issue 标签权重（issue #76）→ issue
  更新时间升序：
  - 入队时记录 issue 标签与 GitLab 更新时间（`tasks.issue_labels` /
    `tasks.issue_updated_at`，webhook 与对账两条路径均落库）
  - 队列内任务按配置 `worker.issue_priority` 的标签顺序排序（默认
    `bug` > `test` > `feature`），未命中配置标签（或无标签）排最后；
    设置页「任务调度」卡片可自定义顺序，修改后对已排队任务即时生效
  - **排队任务人工调优**（issue #242）：任务表 `manual_priority` 字段
    （NULL = 按系统规则）——任务列表页/概览页对排队任务提供「置顶/上移/
    下移/置底/移出队列」操作，调度器派发时 manual_priority 优先于仓库/
    标签规则（先于 issue #287 手动顺序）；移出队列的任务置为终态
    `canceled_by_user`（可手动重试重新入队），操作写入任务日志审计
- 任务持久化到 SQLite，重启后未完成任务按状态恢复：
  - `queued` → 重新入队
  - `running` → 标记为 `interrupted`，按策略重新入队或置为失败
- 状态机：`queued → running → succeeded / failed / retrying /
  canceled_by_user`（issue #242 移出队列终态）

### 5.5 Claude Code 执行器

执行流程：

1. **准备干净工作区**：仓库持久克隆在 `workspace/<repo_name>/`，每次执行前
   （issue #147：模版库「任务开始先校验当前分支切回默认主分支 + 每次开发前
   git pull」两点已下沉为平台代码自动完成，agent 不再自行执行）：
   ```bash
   git fetch origin --prune
   git ls-remote --symref origin        # 解析默认主分支（HEAD 符号引用）
   git remote show origin               # ls-remote 探测失败时的二级探测（HEAD branch: 行）
   # 远端彻底不可达时兜底本地跟踪引用（origin/HEAD → main → master → 字典序），
   # 全程不硬编码 main（issue #148 强化：远端默认主分支可能是 master）
   # 本地缺 refs/remotes/origin/<默认主分支> 跟踪引用时（单分支克隆/受限
   # fetch refspec）先显式拉取补齐，再切回；上游跟踪直接写
   # branch.<名>.remote / branch.<名>.merge（受限 refspec 下 --track 无效，
   # issue #148）
   git fetch origin <默认主分支>:refs/remotes/origin/<默认主分支>
   git checkout -B <默认主分支> origin/<默认主分支>   # 非默认分支时切回
   git reset --hard origin/<默认主分支>
   git clean -fd
   git pull --rebase origin <默认主分支>   # 显式同步远端最新提交
   ```
   （同仓库串行 + 每次重置，从根上消除脏状态和冲突）
   拉取冲突处理（issue #147 补充需求「如果拉取代码的时候出现了冲突，让
   agent 来进行合并」）：`git pull --rebase` 若遇到合并冲突（本地提交与远端
   分叉、untracked 残留被远端新提交占用等），不再直接失败——保留冲突现场
   （rebase/merge 中间态、未合并路径原样保留），并在任务提示词末尾追加
   「先手工解决冲突」指引（git status 查看冲突 → 手工合并 → git add +
   git rebase --continue / git commit），由 agent 完成合并；凭据/网络等
   非冲突失败仍照常报错。
2. **渲染提示词**：取仓库模版（无则用全局），替换变量占位符
3. **注入环境变量**（不写进提示词，避免 token 进入 transcript）：
   - `GITLAB_TOKEN` — 关 issue / 查询用
   - `GITLAB_URL`、`PROJECT_ID`、`ISSUE_IID`
   - 继承服务器已有的 `ANTHROPIC_BASE_URL` / `ANTHROPIC_API_KEY` / `ANTHROPIC_MODEL`
4. **执行**：`claude -p "<prompt>" --output-format stream-json --verbose`（subprocess，工作目录=工作区）。
   逐行 NDJSON 事件（init/assistant/user/result）边运行边 flush，executor
   解析为归一化事件写日志文件 + 发布进程内事件总线（SSE 实时推送）；
   运行一开始（init 行）即拿到 session_id 落库（断点续跑/实时查看）
5. **超时控制**：超过 `task_timeout_seconds` 杀掉进程
6. **结果判定**：
   - exit 0 → 成功
   - exit 非 0 / 超时 / 异常 → 失败，采集 stdout/stderr 尾部日志
7. **重试**：失败后重置工作区重跑，最多 `max_retries` 次；重试仅针对环境性失败（超时、网络、API 抖动），若 Claude Code 明确报告「无法解决」则不再重试
8. **收尾**：仍失败 → 在 issue 留评论（附失败原因 + 日志摘要）+ 打 `bot-failed` 标签，任务标记 failed

### 5.6 提示词模版

变量占位符（渲染时替换）：

| 占位符 | 含义 |
|---|---|
| `{repo_name}` | 仓库名 |
| `{issue_title}` | issue 标题 |
| `{issue_body}` | issue 正文 |
| `{issue_url}` | issue 链接 |
| `{gitlab_url}` | GitLab 地址 |
| `{project_id}` | GitLab 项目 ID |
| `{issue_iid}` | issue 编号 |

示例模版：

```text
你是 {repo_name} 仓库的 AI 维护者。请处理以下指派给你的 issue：

标题: {issue_title}
正文: {issue_body}
链接: {issue_url}

工作要求：
1. 本地工作区已由平台自动切到默认主分支并 git pull 拉取最新代码，
   直接基于最新代码分析问题、定位根因（无需自行切换分支或 git pull）
2. 编写修复代码并自测通过（运行相关测试/构建验证）
3. 自测通过后，直接推送到当前分支（平台已自动切到仓库默认主分支，
   可能是 main / master 等，不要假设分支名）：
   git add -A && git commit -m "fix: 解决（issue #{issue_iid}）" && git push origin HEAD
4. 推送成功后，在 issue 上留结果评论（平台会自动打 bot-done 标签）；
   不要关闭该 issue——关闭动作留给用户确认后手动执行（模版库规范）
5. 提交信息严禁 `fix: #N` / `fixes #N` / `closes #N` / `resolves #N` 等
   「关闭关键词 + #编号」写法：GitLab 实例开启了 autoclose 机制，命中
   默认关闭模式会在推送后自动关闭 issue（用户侧表现为「agent 自己
   close issue」）；issue 引用一律写全角括号 `（issue #N）` 形式。
6. 若确实无法解决，不要推送代码，如实汇报失败原因和已做的尝试

注意：只修改与 issue 相关的代码，不要顺手重构无关部分。
```

### 5.7 Web 管理界面（React）

页面：
- **仓库管理**：仓库列表（启用/停用）、添加仓库（填 GitLab 项目 URL → 自动识别 project_id、注册 webhook、测试连通性）
- **模版管理**：全局默认模版 + 各仓库模版覆盖（含变量说明、实时预览）
- **任务列表**：状态过滤（queued/running/succeeded/failed）、按仓库/issue 搜索
- **任务详情**：提示词原文、exit code、stdout/stderr 日志、重试记录、issue 链接
- **系统设置**：并发数、超时、重试次数、webhook secret（写入 config.yaml）

## 6. 数据库设计（SQLite）

```sql
CREATE TABLE repos (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  gitlab_project_id INTEGER NOT NULL UNIQUE,
  name TEXT NOT NULL,
  url TEXT NOT NULL,
  local_path TEXT,
  prompt_template TEXT,          -- NULL = 用全局模版
  enabled INTEGER DEFAULT 1,
  created_at TEXT DEFAULT (datetime('now'))
);

CREATE TABLE tasks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  repo_id INTEGER NOT NULL REFERENCES repos(id),
  project_id INTEGER NOT NULL,
  issue_iid INTEGER NOT NULL,
  issue_title TEXT,
  status TEXT NOT NULL,          -- queued/running/retrying/succeeded/failed/interrupted/canceled_by_user
  manual_priority INTEGER,      -- 人工优先级（issue #242，NULL=按系统规则）
  attempt_count INTEGER DEFAULT 0,
  triggered_by TEXT,             -- webhook / reconcile
  exit_code INTEGER,
  error_message TEXT,
  log_path TEXT,
  started_at TEXT,
  finished_at TEXT,
  created_at TEXT DEFAULT (datetime('now')),
  UNIQUE(project_id, issue_iid, status)  -- 去重（部分索引：仅对活跃状态）
);

CREATE TABLE task_logs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id INTEGER NOT NULL REFERENCES tasks(id),
  ts TEXT,
  level TEXT,
  message TEXT
);

-- 灵感（issue #131）：概览页「灵感」板块——按仓库随手记录新功能灵感，
-- 仅保存在 Botler 本地数据库，不提交到 GitLab issue
CREATE TABLE inspirations (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  repo_id INTEGER NOT NULL REFERENCES repos(id),
  content TEXT NOT NULL,            -- 灵感内容（去首尾空白后非空且 ≤ 5000 字）
  created_at TEXT DEFAULT (datetime('now')),
  updated_at TEXT DEFAULT (datetime('now'))
);
```

## 7. 安全设计

- **凭据管理**：GitLab bot token、webhook secret、DeepSeek key 全部存环境变量（`.env`），config.yaml 引用变量名；不入库、不进日志、不进提示词
- **token 传递**：`GITLAB_TOKEN` 只通过子进程环境变量注入 Claude Code，防止出现在提示词 transcript 中
- **webhook 校验**：`X-Gitlab-Token` 与 secret 比对，防伪造请求
- **工作区隔离**：每次执行前 `reset --hard` + `clean -fd`；不同仓库工作区互相独立
- **Claude Code 权限**：通过 settings.json 配置 allowlist（允许 `Bash(git:*)`、`Bash(curl:*)` 等任务所需命令），默认拒绝其他；无头模式禁止交互提权
- **风险认知**：main 不保护 + bot 直接推 = 单点失误可能破坏 main。缓解：同仓库串行、干净工作区、提示词强调「自测通过才推」；个人自用可接受

## 8. 部署方案（10.0.0.122）

前置条件：
1. Node.js 18+（Claude Code 运行依赖）
2. 安装 Claude Code：`npm install -g @anthropic-ai/claude-code`
3. 配置 DeepSeek 环境变量（Claude Code 兼容端点）：
   ```bash
   export ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic
   export ANTHROPIC_API_KEY=sk-xxxx          # DeepSeek API key
   export ANTHROPIC_MODEL=deepseek-chat
   ```
   > ⚠️ 注意：若服务器配置了代理，跑 `claude -p` 前需确保代理环境变量已清理（否则报 TLS 证书错误），与 macOS 本机遇到的坑一致。
4. 网络：确认 10.0.0.122 能访问 `home.chenkaidi.top:509`（GitLab）及 GitLab 服务器能反向访问 10.0.0.122 的 webhook 端口（同一 ZeroTier 网络应互通）
5. bot 账号 token：scope `api` + `write_repository`；bot 账号加入各目标仓库（角色 Maintainer）

平台部署：
1. `git clone` 平台代码到 10.0.0.122
2. `pip install -r requirements.txt`、`npm install && npm run build`（前端构建产物由 FastAPI 托管）
3. 配置 `.env`（bot token / webhook secret / DeepSeek key）与 `config.yaml`
4. 启动：pm2（`pm2 start` + `pm2 save` + 开机自启）或 systemd
5. 在 Web UI 添加仓库 → 平台自动注册 webhook
6. 冒烟测试：手动把一个小 issue 指派给 bot，验证全链路

## 9. API 设计（FastAPI）

```
GET    /api/health                    健康检查
GET    /api/repos                     仓库列表
POST   /api/repos                     添加仓库（自动识别 project_id + 注册 webhook）
PUT    /api/repos/{id}                更新仓库（启用/停用/模版覆盖）
DELETE /api/repos/{id}                删除仓库
POST   /api/repos/{id}/test           测试连通性（token 有效性 + webhook 状态）
GET    /api/repos/{id}/template       获取仓库模版
PUT    /api/repos/{id}/template       更新仓库模版
GET    /api/settings                  系统设置
PUT    /api/settings                  更新设置（写入 config.yaml）
GET    /api/tasks                     任务列表（分页/过滤）
GET    /api/tasks/{id}                任务详情（含日志）
GET    /api/tasks/{id}/logs           任务日志
POST   /webhook/gitlab                接收 GitLab webhook（secret 校验）
```

## 10. 开发里程碑

**Phase 1 — MVP（核心闭环）**
- FastAPI 骨架 + config.yaml 加载 + SQLite 模型
- GitLab 集成层（token 认证、issue API、webhook 注册）
- Webhook 接收器 + 简单串行队列
- Claude Code 执行器（提示词渲染 + 干净工作区 + 超时）
- 失败重试 + issue 失败评论
- 验证标准：手动指派 issue → 代码推上 main → issue 自动关闭

**Phase 2 — 健壮性**
- 跨仓库并行 + 每仓库串行队列
- 对账兜底调度器
- 任务状态机 + 重启恢复
- 日志采集与落盘

**Phase 3 — Web UI**
- React 前端：仓库管理、模版管理、任务列表/详情、设置页
- 鸿蒙端（issue #173）：HarmonyOS NEXT Web 套壳，复用 Web 前端全部能力，
  CI/CD 加入 hvigorw 鸿蒙编译（harmony:build）

**Phase 4 — 打磨**
- 任务统计、异常告警（可选）、并发压测调参

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| DeepSeek 兼容端点模型能力弱于 Claude 原版 | 修复质量波动 | 模版强调自测；模版可切回 Claude 官方模型（环境变量可换） |
| Claude Code 推坏 main | 代码损坏 | 同仓库串行 + 干净工作区 + 模版约束；个人自用可接受，后续可加保护 |
| webhook 丢失 | 任务漏处理 | 对账兜底每 5 分钟扫描补漏 |
| 平台重启中断任务 | 任务悬挂 | 状态机：running → interrupted 恢复 |
| 重试消耗 DeepSeek token | 成本 | 重试上限 2 次；明确「无法解决」不重试 |
| GitLab 无法回调 webhook（网络隔离） | 完全失效 | 部署前先验证 10.0.0.122 ↔ GitLab 双向连通 |
