# 在 GitLab 页面查看静态分析扫描结果

> issue #86：CI 的 security 阶段扩展为 5 个并行 job（bandit /
> pip-audit / npm audit / semgrep / gitleaks），覆盖前后端「代码
> SAST + 依赖 CVE + 密钥泄露」三个维度。本页说明各工具扫描结果
> 在 GitLab 网页界面的查看入口、阻断规则与误报豁免方式。

## 扫描矩阵一览

| Job | 工具（免费开源） | 扫描对象 | 报告类型 | 阻断规则 |
|-----|-----------------|---------|---------|---------|
| `security:bandit` | bandit | 后端 Python 代码 | SAST（SARIF） | 中危（medium）及以上 |
| `security:deps-python` | pip-audit | 后端依赖 requirements.txt | 依赖扫描 | 任何已知 CVE（保守按中危） |
| `security:deps-frontend` | npm audit | 前端依赖 package-lock.json | 依赖扫描 | moderate（中危）及以上 |
| `security:semgrep` | semgrep 社区版 | 前后端代码（Python + JS/TS） | SAST（SARIF） | ERROR/WARNING（高危/中危） |
| `security:secrets` | gitleaks | 全仓库工作区（密钥/凭据） | SAST（SARIF） | 任何发现 |

所有报告均为 `when: always` 上传——门禁因漏洞失败时，页面同样
展示被阻断的漏洞详情。

## 查看入口

### 1. 流水线 Security 标签页（最常用）

`项目页面 → 构建 → 流水线 → 点击某次流水线 → Security 标签`。

- 列出该次流水线全部安全扫描结果（SAST 与依赖扫描分栏展示），
  显示各扫描器发现的漏洞数与严重级别分布；
- 点击扫描器条目查看每条漏洞详情：规则编号、严重级别、所在文件
  与行号、触发代码片段（依赖扫描另含受影响版本范围与修复建议）；
- 门禁失败的流水线可直接跳转漏洞详情，与 job 日志同屏对照。

### 2. Merge Request 安全组件

创建 MR 时，MR 页面自动展示 **Security scanning** 组件，列出本次
变更**新增**的漏洞（与目标分支比较），全部修复时显示绿色
「No vulnerabilities found」。

### 3. 直接下载原始报告

流水线各 security job 右侧「浏览产物」按钮可下载原始报告文件
（保留 1 周）：

- `backend/bandit-report.sarif`（bandit）
- `backend/deps-python-report.json`（pip-audit 转换后）
- `frontend/deps-frontend-report.json`（npm audit 转换后）
- `backend/semgrep-report.sarif`（semgrep）
- `gitleaks-report.sarif`（gitleaks）

## 阻断判定细节

| 工具 | severity 来源 | 高危 | 中危 | 低危/Info |
|------|--------------|------|------|----------|
| bandit | 内置置信度分级 | 阻断 | 阻断 | 仅记录 |
| pip-audit | 输出不含 severity | 任何已知 CVE 保守按中危阻断（见下） | | |
| npm audit | 输出自带（low/moderate/high/critical） | 阻断 | 阻断 | 仅记录 |
| semgrep | 规则内置（ERROR/WARNING/INFO） | 阻断 | 阻断 | 仅记录 |
| gitleaks | 无分级 | 任何发现即阻断 | | |

> **pip-audit 为何「任何 CVE 都阻断」？** pip-audit 的数据源
> （PyPI JSON API / OSV）不提供 severity 字段，报告的均为已公开
> 的已知漏洞（PYSEC/GHSA/CVE 编号）。为避免「无法定级」变成
> 「静默放行」，保守策略按中危处理并阻断。可人工评估后用
> `PIP_AUDIT_IGNORE` 豁免（见下）。

## 误报与豁免

### 审计服务不可用（自动放行）

依赖扫描依赖外部审计服务（PyPI / OSV / npm audit 端点）。服务
不可用时（转换脚本 exit 2）job 自动切换备用数据源重试，仍失败
则**警告放行不阻断**（基础设施故障不应卡死流水线），日志中会
提示「本次放行不阻断」。可稍后手动重跑该 job 补扫。

### pip-audit 豁免（CI 变量）

`Settings → CI/CD → Variables` 添加 `PIP_AUDIT_IGNORE`，值为逗号
分隔的漏洞 ID（如 `PYSEC-2024-38,GHSA-xxxx`）。豁免的漏洞不进
报告、不阻断。**仅用于人工评估确认不受影响的漏洞。**

### npm audit 豁免（CI 变量）

`NPM_AUDIT_IGNORE`：逗号分隔的包名，豁免该包全部漏洞
（如 `react,esbuild`）。

### semgrep 误报豁免

在触发行的行内注释 `# nosemgrep` 即可豁免该行（Python/JS 通用）。
规则本身位于 `ci/semgrep-rules.yaml`，新增/调整规则随代码评审进行。

### gitleaks 误报豁免

`ci/gitleaks.toml` 的 `allowlist`：

- `paths`：排除目录/文件（正则），目前排除运行时数据目录
  （data/、workspace、node_modules、构建产物等）；
- `regexes`：豁免特定密钥模式（目前含测试 fixture 的示例
  PAT `glpat-owner-1234567890`）。

新示例凭据（测试 fixture 等）应在此登记；真实密钥必须轮换并
从代码中移除，不得豁免。

## 常见问题

- **为什么 job 失败还能看到报告？** 阻断失败正是「发现了高危/
  中危问题」，此时更需要看到漏洞详情，因此报告配置为
  `when: always` 上传。
- **依赖扫描的「文件」为什么是 requirements.txt / package-lock.json？**
  审计工具以依赖声明文件为扫描入口，漏洞定位到具体包与受影响
  版本范围，而非源码行。
- **semgrep 为什么扫描跑两遍？** 第一遍（--json）做阻断判定并
  检查规则文件健康（解析失败必须 fail，防止规则失效假绿）；
  第二遍（--sarif）生成 GitLab SAST 报告上传。
- **流水线因漏洞被阻断怎么办？** 按漏洞详情升级依赖或修复代码，
  重新推送即触发新一轮扫描；确认不影响可走上述豁免通道。
